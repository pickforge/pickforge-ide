# vibe-flutter — Brainstorming Notes

Working memory for this project. Updated as we go.

## Vision (user's words)

A local desktop app, **built in Flutter**, that helps you "vibe code" Flutter apps (and maybe other languages later) by giving the AI rich *widget-level* context from a running app.

Core loop the user described:
- User runs their Flutter app in an emulator (or a web session simulating mobile).
- User hovers over the running app → widgets are auto-detected and outlined (like Flutter DevTools inspector).
- User clicks to select a widget / screen region.
- App extracts that widget's source code + context and feeds it to an AI coding agent.
- AI makes **surgical, precision edits** to that specific widget.
- Optionally: before/after screenshots are sent to the AI so it "sees" the visual change.

Runs locally. Spawns the user's own Claude Code / Codex / OpenCode in a terminal, using their own credentials, but enriched with widget context.

## Reference: BridgeSpace (bridgemind.ai)

The user wants something **inspired by** BridgeSpace but Flutter-focused.
- BridgeSpace = Tauri v2 + React 19 desktop app, multi-pane terminals, AI agent orchestration, built-in editor, command blocks, task board.
- **BridgeSwarm** is especially interesting to the user: multi-agent orchestration — builder / reviewer / scout / coordinator roles, shared mailbox, parallel work.
- BridgeSpace is paid ($20/mo). User is wondering: freemium? free? Worth monetizing?

## Key differentiator vs BridgeSpace / Cursor / Warp

**Widget-level selection from a live running app** is the novel piece. Nobody else is plugging Flutter widget context directly into an agent's prompt.

## Open questions (to work through)

- MVP scope: just the widget-pick → agent flow, or also terminals / editor / swarm?
- Which agents to support first (Claude Code only, or multi)?
- How do we get the widget tree from the running app — VM Service, DevTools protocol, or the VGV MCP `get_widget_tree` tool?
- Platform scope: Flutter targets (mobile/web/desktop emulators) — which first?
- Monetization: free, freemium, paid?

## Decisions log

- **MVP scope = C.** Widget-picker + a single embedded Claude Code / agent terminal pane. No swarm, no editor, no task board, no multi-pane terminals. The loop is: run app in embedded/attached emulator → pick widget → inject context into the one agent pane → see the edit → hot reload → verify visually. Workspace/swarm features are explicitly deferred to post-MVP.
- **Widget-tree transport = VM Service + Flutter Inspector protocol (`ext.flutter.inspector.*`).** Same mechanism DevTools uses. Zero user setup — they just run `flutter run` normally; we attach over WebSocket. The picker queries the widget tree and creation locations (file + line) directly. The embedded *agent* gets the existing `vgv-ai-flutter-plugin` MCP tools (hot_reload, get_widget_tree, analyze_files, etc.) for its own actions. No custom Dart package required.
- **License = MIT, open core.** Widget picker + single-agent pane ships under MIT from day one. Users bring their own Claude Code / Codex / OpenCode creds, so we have zero API cost. Paid pro tier (swarm, team sync, cloud context, premium skills) is a post-MVP decision and lives behind a feature flag or separate repo. The $1k marketing budget is better spent on landing-page polish and organic demo distribution (HN, Product Hunt, Flutter Weekly, a viral widget-picker GIF) than on paid ads for a niche tool.
- **Platform scope = Android emulator first.** iOS and web are trivial follow-ups because the VM Service + Inspector protocol is identical across targets; the scope cost is in docs/QA, not code. Demo video is a mobile app getting live-edited.
- **Product name = Pickforge.** Domain: `pickforge.dev` ($10-15/yr, Google-owned, HTTPS-enforced, developer-native TLD). Repo stays `vibe-flutter` for now; product/brand = Pickforge. ".ai" rejected as overkill ($80/yr for no meaningful brand benefit — AI is plumbing here, not the product identity).
- **Agent support = Claude Code + Codex + OpenCode from day one.** Architected as an `AgentProfile` abstraction (binary, invocation flags, context-file name, system-prompt flag, prefill strategy, MCP config path). One engine, three profiles. Future agents = new profile, ~days of work each.
- **Context delivery = hybrid, stdin/new-terminal first.** On widget pick, Pickforge spawns a new OS-native terminal (respecting `$TERMINAL` on Linux, `Terminal.app`/iTerm on macOS, `wt.exe` on Windows) running a generated wrapper script that: (1) cd's into the project, (2) writes a per-invocation skill + AGENTS.md/CLAUDE.md to a scoped dir, (3) invokes the chosen agent CLI with the pre-filled first message. MCP server path comes in Phase 1.5 for richer interactions (agent re-queries widget tree mid-task).
- **Skill / injected-context licensing = P1 (public skills, value is UX).** All injected skills and AGENTS.md templates live in the OSS repo under MIT. This matches how Aider, Continue.dev, and OpenCode already distribute prompt templates — nobody forks these projects just for the prompt text; the value is the integrated experience. Pickforge Pro (post-MVP) differentiates on **swarm, team sync, cloud context, priority support** — NOT on secret prompts. Community PRs to improve skills become a strength, not a leak.
- **Skill layout = small library, seeded with 3 + 1.** Not a single mega-file. The MVP ships:
  - `skills/edit-widget.md` — modify a selected widget's appearance/behavior in place.
  - `skills/extract-widget.md` — extract the selected subtree into its own widget class.
  - `skills/explain-widget.md` — describe what the selected widget does / trace its data flow.
  - `AGENTS.md` (or per-agent equivalent) — general project context (detected from `pubspec.yaml`, lint config, folder structure) plus Pickforge usage rules.
  All agent profiles point to the same skill source; per-agent templates wire them into that agent's native skill/context mechanism.
- **MVP shape = Approach A (external dock + on-device select mode).** Pickforge is a small, always-on-top Flutter desktop window that runs next to the user's Android emulator. Attaches to VM Service, flips on Flutter Inspector's "Select Widget Mode" (the same mechanism DevTools uses), user taps in the emulator, Flutter's own on-device inspector draws the highlight, Pickforge receives the selection over the Inspector protocol. Pickforge's window renders: widget tree, last-screenshot preview, selected-widget details, skill picker, "Forge it" button. No embedded emulator mirror, no custom pixel overlay, no scrcpy — those are deferred to Phase 2 ("Pickforge Pro" polish). Approach A code is a strict subset of the Approach B code, so Phase 2 adds, it doesn't rewrite.
- **Package stack (confirmed with user):**
  - Runtime: `flutter_bloc`, `bloc`, `equatable`, `freezed_annotation`, `json_annotation`, `get_it`, `injectable`, `go_router`, `drift`, `drift_flutter` (or `sqlite3_flutter_libs`), `dio`, `vm_service`, `web_socket_channel`, `window_manager`, `path_provider`, `path`, `yaml`, `shared_preferences` (thin settings only).
  - Dev: `build_runner`, `freezed`, `json_serializable`, `injectable_generator`, `drift_dev`, `mocktail`, `bloc_test`, `very_good_analysis`, `test`, `flutter_test`.
  - **DI style:** GetIt + Injectable for service/repo/bloc registration. `flutter_bloc`'s `BlocProvider` still used inside the widget tree for scoping cubits to routes; repositories are pulled from GetIt, not RepositoryProvider. This is a valid hybrid, just different from stock VGV examples.
  - **Storage:** Drift from day one (user preference). Initial schema covers `pick_history`, `project_settings`, `agent_run_log`. `shared_preferences` only for lightweight/bootstrap settings (e.g. last-used project path).
  - **Networking:** Dio is included in the stack but has **no confirmed MVP use case**. Flagged for re-evaluation — see notes. Likely first real use is update-check and (post-MVP) Pickforge Pro auth / cloud skills fetch.
- **TerminalProfile registry.** Sibling abstraction to `AgentProfile`. Bundles launcher profiles for Ghostty, iTerm2 (macOS), Warp (URL-scheme launch), WezTerm, Alacritty, Kitty, Windows Terminal, gnome-terminal, Terminal.app, plus an `$TERMINAL` fallback. On first run, Pickforge detects installed terminals and pre-selects the most capable (Ghostty > WezTerm > Alacritty > platform default). User-selectable in Settings. **Superseded 2026-04-25** — see "Embedded terminal pane (Option A)" decision below. The registry, profiles, detector, terminal picker UI, and the terminal-launching half of `WrapperScriptGenerator` are removed; the `.pickforge/`-writer half stays. The salvageable UX (font family, font size, color theme) moves to a new `EmbeddedTerminalSettings`.

- **Context injection = scoped `.pickforge/` folder, never touch user's CLAUDE.md/AGENTS.md.** Pickforge writes `.pickforge/skill-active.md`, `.pickforge/widget-context.md`, `.pickforge/screenshot.png`, `.pickforge/device-screen.png`, `.pickforge/run-log.json` to the project root. Auto-generates a `.pickforge/.gitignore` containing `*` on first run. The initial prompt to the agent tells it to `Read` these files. Agent's own `Read` tool is the uniform API; no CLI-flag variance between Claude Code / Codex / OpenCode. User's own `CLAUDE.md` / `AGENTS.md` coexist untouched and are read by the agent as normal.
- **Screenshots = dual capture on Android.** Primary: `ext.flutter.inspector.screenshot` (clean widget surface, platform-agnostic). Secondary (Android only, when `adb` is available): `adb -s <serial> exec-out screencap -p` written to `.pickforge/device-screen.png`. The adb shot shows the selection highlight box + system UI, giving the agent a "this one" visual ground-truth. Both paths sent in the prompt. iOS equivalent (`xcrun simctl io booted screenshot`) deferred per Q4.
- **Design quality is a first-class requirement, not a polish pass.** Target aesthetic is the 2026 power-user dev-tool pocket (Linear, Raycast, Arc, Cursor, Zed, Warp, Ghostty, BridgeSpace). Dark-first with chromatic accent (forge-ember orange or electric violet TBD), Liquid Glass / glassmorphism on floating panels, dense-but-breathable rhythm on an 8px grid, ~13px body, Geist/Inter for chrome + Berkeley/JetBrains Mono for code, subtle noise overlays on dark surfaces, ⌘K command palette as the primary nav, semantic (not decorative) color. No Material 3 defaults — `ThemeData` fully overridden. Motion uses spring physics, is always causally meaningful, respects OS reduce-motion, uses skeletons over spinners. Empty/waiting states animate. Hero transitions between widget picks and the details panel. All animation via `flutter_animate` + Flutter's official `animations` package + `rive` for hero brand motion (Lottie optional later). Budgeted ~2 extra weeks of polish in MVP. Design quality IS the moat for an OSS tool competing with a funded closed paid competitor — underspending here defeats the thesis.
- **Architecture style = feature-first single-package.** `lib/features/<name>/` per feature (connection, widget_picker, forge, history, settings). `lib/core/` for tech infrastructure (vm_service, drift, agent, terminal, skills, inspector). `lib/shared/` for cross-feature widgets/theme/motion. `lib/l10n/` for ARB files. VGV's multi-package layered architecture is a post-MVP refactor.
- **Localization = wired day one, English-only MVP.** `flutter_localizations` + `intl` + `intl_utils`. Every user-visible string goes through `context.l10n.someKey`. Adding pt-BR/es/ja later is ARB-file-only.
- **Icon set = Lucide (primary) + Hugeicons (fallback).** Lucide matches the reference aesthetic (Linear, Raycast, Vercel, Supabase, shadcn all use it). Hugeicons fills gaps where Lucide lacks an icon.
- **Paid tier backend committed = Supabase** (Postgres + RLS, Auth, Storage, Edge Functions, Realtime). Not wired in MVP — locked in for Phase 2 / Pickforge Pro so we don't rebike-shed the backend decision later.
- **Project = a Flutter app folder on disk.** A Pickforge "project" is a directory containing a `pubspec.yaml`, identified by its absolute `projectRoot` path. All chats, forge history, picks, and settings hang off `projectRoot`. Connecting to a running VM service is a per-session action *on* a project — the same project can be connected to different emulators across different days, but the project itself is the folder. Matches today's `ProjectSettings` keying so persistence migration is mechanical (just add the new columns/tables). Rejected alternatives: (b) project = saved connection (loses one-to-one with the codebase, "the same folder = one project" intuition), (c) project = folder + nested workspaces (BridgeSpace-style — more concepts to teach; can be added later as a sub-list under each project without re-architecting). 
- **Chat = persistent terminal session per project (one live PTY per chat).** A project owns N chats; each chat is a single long-running PTY session bound to the user's chosen agent CLI (Claude Code / Codex / OpenCode), running in their native interactive REPL mode. The sidebar lists chats per project; "+ New Chat" spawns a fresh PTY; switching chats swaps the visible terminal pane to that chat's PTY (others stay alive in the background, capped — see below). "Forge It" on a widget pick injects a new prompt into the *currently-focused* chat's PTY, not a new process. Closing Pickforge tears down all PTYs; reopening replays the persisted scrollback visually so the chat *looks* continuous, but the underlying agent session is gone — multi-turn continuity across app restarts relies on each CLI's own `--resume` mechanism, applied lazily (when the user types in a "cold" chat, Pickforge re-spawns the CLI with `--resume <session-id>` if the agent supports it). Persistence: chats table keyed by `(projectRoot, chatId)` with title, agentId, sessionId (for resume), createdAt, lastActivityAt, plus a transcript log (raw bytes or stripped text — see scrollback decision). Background-PTY cap: TBD in next question. Rejected: (b) one-shot PTY per Forge (loses interactive feel, mismatches what "chat" means in the sidebar), (c) one PTY per project with chats as bookmarks (too constrained — switching chats requires killing the agent).
- **PTY lifecycle = all chats in the active project stay alive; switching projects parks them.** Switching between chats *within* the active project is instant — every chat in that project has a live PTY in the background. Switching projects parks (kills) every PTY of the outgoing project and, for the incoming project, replays each chat's persisted scrollback to the renderer; PTYs are spawned lazily per chat on first input (using each CLI's `--resume <session-id>` so the agent picks up where it left off). Quitting Pickforge tears down all PTYs cleanly (SIGTERM with a short grace, then SIGKILL). Resource bound is therefore "however many chats are in the active project," which scales with the user's own working-set, not a magic number — predictable and self-limiting. Cost-saving optimizations rejected for v1: (b) global LRU cap of N concurrent PTYs (unpredictable cold-switches surprise the user), (c) only-visible-chat-is-live (every chat switch eats a 0.5–1.5s CLI cold start — bad for the "hammer the sidebar" power-user motion). Both can be added later behind a Settings toggle if telemetry shows real users have huge per-project chat counts.
- **Scrollback persistence = stripped UTF-8 text + ANSI color-span sidecar (Option b).** What goes on disk per chat is plain searchable text plus a thin per-segment metadata stream describing color/bold/underline spans, NOT the raw byte stream. The live PTY → xterm.dart pipe is unaffected (it still sees raw bytes for the active session); persistence sits *next to* the PTY tap and decides what to serialize. On chat reopen, the renderer replays text + re-applies color spans — visually faithful for normal agent output (assistant text, syntax-highlighted code blocks), gracefully degrades for TUI redraws (vim, plan-mode dialogs, spinners) which never make it into a real terminal's scrollback either, so the loss matches user expectation. Wins: ~10× smaller disk footprint than raw-byte capture (matters with dozens of chats), enables full-text search across chat history (a real product feature — "where did the agent suggest the BLoC pattern?"), human-readable for debugging / DevTools / `cat`. Cap: per-chat budget (start with 5 MB stripped text + sidecar; older content truncated from the head, oldest-first). Storage shape: per-chat append-only log file under `<projectRoot>/.pickforge/chats/<chatId>/transcript.log` for text and `transcript.spans.bin` (or jsonl) for the color sidecar — keeps Drift focused on small relational metadata and avoids stuffing megabytes into SQLite blobs. Rejected: (a) raw PTY bytes (search-hostile, ~10× disk, perfect replay we don't need for offline scrollback), (c) hybrid raw-recent + stripped-old (most complex, marginal gain over (b)).
- **ForgePanel lives above the terminal in the middle pane.** New layout: left = projects + chats sidebar, middle = a Scaffold containing forge controls (skill picker, agent picker, "Forge It" button) as the chat's compose-bar header *plus* the embedded PTY terminal beneath it, right = pure widget inspector (tree + details + screenshot). "Forge It" generates the same skill/widget-context bundle as today and pipes the resulting initial-prompt into *this chat's* live PTY (instead of spawning a new external terminal). Rationale: forge is conceptually "send a prompt to the agent," so it belongs next to the agent's terminal; right pane staying pure inspector matches the user's "left = nav / middle = work / right = context" mental model; the wrapping Scaffold incidentally fixes the existing `ScaffoldMessenger.of(...)` bug in `ForgePanel` (no current Scaffold ancestor in `dock_view`'s tree). Rejected: (b) bottom of right pane (visually splits forge from where its output lands; clutters the inspector), (c) floating sheet over the terminal when a widget is picked (less discoverable for the always-on flow we're designing for).
- **Three-pane shell layout confirmed.** Persistent app shell (replaces today's full-screen `DockView`-as-route): left rail (220px-ish, resizable) = projects list with active-project highlight + chats list under the active project + "+ New chat" + "+ Add project"; middle pane (flexible, primary) = a Scaffold whose top bar is the forge compose strip (skill chip · agent chip · "Forge It" button) and whose body is the embedded PTY terminal pane; right pane (320px-ish, resizable, collapsible) = pure widget inspector content (selected widget props block, device screenshot, widget tree with selection highlight). Pane sizes are persisted per-user. The shell wraps every "in a connected project" route; `ConnectionView` and `SettingsView` remain full-bleed routes outside it. Mockup: `.superpowers/brainstorm/.../three-pane-shell.html`.
- **VM-service connection = per-project, optional, auto-attempted on project select.** Project = folder on disk; VM service = ephemeral emulator runtime. They're decoupled. Selecting a project triggers a silent background reconnect to that project's last-known `vmServiceUrl` (already in `ProjectSettings`). Success → inspector pane lights up with live widget tree / selection / screenshot. Failure (timeout, ECONNREFUSED, stale token) → inspector pane shows an empty state with the existing `DiscoveredDevicesList` widget inline plus a manual URL field; the terminal pane and chats keep working unaffected so the user can read past transcripts or chat with the agent even without an emulator (huge win — "ask the agent something about my codebase" no longer requires `flutter run`). Connection state surfaces as a small status pill in the right-pane inspector header (e.g., `● connected · Pixel_5` / `○ disconnected` / `↻ reconnecting…`); clicking it opens a menu with reconnect / pick different device / disconnect. `ConnectionView` is removed as a gateway route — the shell is the entry point; manual VM-service connection is now an *inside-the-shell* action via the inspector pill, not a separate page. Rejected: (b) global gateway connection (forces emulator-first flow that breaks chat-without-emulator and "browse my projects offline"), (c) per-chat connection (over-flexible — users think one project = one emulator session, per-chat bindings are noise).
- **PTY stack = `xterm` (terminal renderer) + `flutter_pty` (native PTY) on pub.dev, both from publisher `terminal.studio`.** Verified current state (2026-04-25): xterm 4.0.0 — MIT, 235 likes / 150 pub points / 195k downloads, supports Android/iOS/Linux/macOS/Windows/web, last publish ~2y ago (mature, not abandoned — feature-complete with sporadic fixes). flutter_pty 0.4.2 — MIT, 23 likes / 150 pub points, all desktop + mobile, last publish ~15mo ago, wraps native forkpty/openpty on Unix and ConPTY on Windows (not pure FFI — actual native plugin code, more stable than DIY FFI). Both from the same verified publisher (`terminal.studio`) so they're co-designed; if either stalls, vendoring is straightforward (MIT, small surface). Rejected: (b) DIY FFI/Rust PTY layer (months of work re-implementing what `flutter_pty` already does, including ConPTY quirks; only justified if `flutter_pty` proves blocking), (c) non-PTY stdin/stdout pipes (defeats the point of Option A — agent CLIs detect "no TTY," disable colors, plan-mode dialogs and TUI features break). Risks accepted: (1) flutter_pty maintenance cadence is light — vendor it the moment a Dart 4 / Flutter SDK bump breaks it rather than blocking on upstream; (2) xterm 4.0 has been stable but a Flutter framework breaking change could need a fork — same vendoring plan applies; (3) one or two known platform quirks documented in xterm/flutter_pty issue trackers (e.g. Windows ConPTY edge cases on resize) we'll discover empirically and patch as they come up.

- **Embedded terminal pane (Option A) replaces external-terminal launching entirely.** The previously-shipped flow — Pickforge writes a wrapper script, spawns Ghostty/WezTerm/etc. as a child process, agent CLI runs in that external window — is removed. Pickforge becomes the terminal: a real PTY-backed pane inside the app (xterm.dart + flutter_pty) runs the agent CLI exactly as Ghostty would, so TUI / vim / plan-mode dialogs / slash menus all work unchanged. Rationale: pre-1.0 = no users to migrate; two paths is the most expensive shape (every feature must handle both); the "escape hatch" argument removes the pressure to make the embedded pane genuinely good; the future Option B chat adapter doesn't need the external-terminal path either, so keeping it preserves code with no architectural home. Files removed: `TerminalProfileRegistry`, `TerminalProfile` model, all per-OS terminal profiles (Ghostty/WezTerm/iTerm/Warp/Windows Terminal/Alacritty/Kitty/gnome-terminal/Terminal.app), `terminal_detector.dart`, the terminal picker UI in ForgePanel, and the *terminal-launching* half of `WrapperScriptGenerator` plus their tests. Files kept: the `.pickforge/`-writer half of context generation (skill, widget-context, screenshots, initial-prompt) — agents still read those at startup. Salvaged: a new `EmbeddedTerminalSettings` (font family, font size, color theme) under `lib/core/terminal/`, exposed in Settings, applied to xterm.dart's renderer. Reversibility: if external-terminal demand resurfaces post-launch, git history has the deleted code.

## Explicitly deferred to Phase 2 / post-MVP

Track these so we don't forget the follow-up after the MVP ships.

- **Approach B (embedded emulator mirror + custom overlay):** scrcpy integration, DPR math, input forwarding. The "hero demo" polish version of Approach A.
- **True hover-over-the-screen UX:** currently hover works only over Pickforge's own widget-tree and screenshot panels. Real hover over the live emulator requires Approach B.
- **Target expansion beyond Android emulator:** iOS Simulator, Flutter web (Chrome), Flutter desktop targets. Code is platform-agnostic; scope cost is docs + QA + edge cases.
- **Agent expansion:** Cursor CLI, Gemini CLI, future CLIs. Each = new `AgentProfile` + test.
- **Phase 1.5 — Pickforge MCP server:** expose `get_selected_widget`, `list_pickforge_history`, `capture_screenshot` etc. so agents can re-query state mid-task (e.g., verify their own hot-reload change).
- **Pickforge Pro tier:** BridgeSwarm-style multi-agent orchestration, team sync, cloud-synced context, priority support, premium skill packs. Paid. Lives behind a feature flag or separate repo. Monetization stays open (freemium vs paid) until we have MVP users.
- **Dio wiring:** package included but unused in MVP. First likely use: update-check on startup. Post-MVP: Pro auth, cloud skill packs.
- **Auto-discovery of VM Service URL:** MVP is manual paste. Phase 2: port scan common `flutter run` ports and/or hook into `flutter daemon` for zero-setup discovery.
- **Rebuild tracking:** `ext.flutter.inspector.trackRebuildDirtyWidgets` to show "here's what changed after hot-reload" as a diff in Pickforge's UI.
- **Skill overrides + community skill packs:** `.pickforge/skills/` project-local override works day-one; a registry/market of community-contributed skills is Phase 2.
- **Telemetry + crash reports (Sentry).** Off by default, opt-in toggle.
- **Auto-updater:** Sparkle on macOS, winget/scoop on Windows, `.deb`/AppImage refresh on Linux.
- **Codesigning / notarization / distribution:** macOS notarization, Windows signing cert + SmartScreen reputation, Linux Flathub/Snap listing. Release engineering, not MVP code.
- **Widget-tree diffing between runs:** "here's what changed since the last pick" — nice polish.
- **Screenshot before/after pair sent to the agent:** MVP sends the *before* screenshot with the pick; auto-capturing an *after* screenshot post-hot-reload and re-prompting the agent with "did your change look right?" is Phase 2.
- **Embedded chat-style agent pane (Option B — headless adapter, no PTY).** Today (and v1 of the embedded terminal) Pickforge runs the agent CLI in a real PTY (xterm.dart + flutter_pty), so the user gets the full TUI exactly as in Ghostty/WezTerm. A future, *bigger* alternative is to render the agent conversation as a custom Pickforge-owned chat UI (bubbles, inline widget-pick attachments, screenshots-as-images, per-project searchable history, branchable threads, swarm-friendly), still **without ever handling user credentials or API keys**. Mechanism: invoke each CLI in its native headless mode and parse its structured event stream — `claude -p "<prompt>" --output-format stream-json` (Anthropic-blessed flow), `codex exec` with JSON output, `opencode run` with JSON output. Multi-turn continuity uses each CLI's own `--resume <session-id>` mechanism. Auth stays inside `~/.claude` / `~/.codex` / `~/.config/opencode` — Pickforge never sees tokens. Cost: one *adapter* per CLI (headless-flag mapping + JSON event → normalized `ChatMessage` model), feature-parity drag for TUI-only flows (slash menus, plan-mode dialogs, in-CLI editor pop-ups), per-turn cold-start cost, and a maintenance burden when a CLI's headless schema evolves. Worth doing only when the value prop becomes "Pickforge owns the conversation" (inline pick attachments, persistent project-scoped chat history, branching, swarm orchestration) — for "stop opening a separate terminal window," Option A is sufficient. Suggested staging: Claude Code adapter first (most mature `stream-json`), then Codex, then OpenCode — each behind a per-agent feature flag so Option A remains the default.
